# Green Desktop — Design Document

## What it is

A minimal desktop VPN client for macOS and Windows. The user pastes one or more VLESS keys,
picks one, and clicks Start. The app routes traffic through xray-core running as a local
SOCKS5/HTTP proxy. No installer wizard, no telemetry, no account.

---

## High-level architecture

```
┌─────────────────────────────────┐
│  Compose Multiplatform UI (JVM) │
│  AppViewModel  ←→  AppState     │
└────────┬──────────────┬─────────┘
         │              │
    XrayProcess     SysProxy
         │
    ┌────▼────────────────────┐
    │  xray binary (subprocess)│
    │  - key2json subcommand   │  ← generates config from vless:// URI
    │  - run subcommand        │  ← runs the proxy
    └──────────────────────────┘
```

The UI and the proxy are entirely separate processes. The Kotlin app manages xray's lifecycle;
xray handles all network traffic. They never share memory — the only interface is:
1. `xray key2json` on startup to produce a config file
2. `xray run -c config.json` to run the proxy
3. gRPC API on `localhost:8888` for stats (up/down bytes)

## Components

### `Main.kt` — entry point

- Sets `apple.awt.UIElement=true` so the app is a macOS accessory (no Dock icon).
- Sets `apple.awt.application.name=Green` so the window switcher shows the right name.
- Creates the system tray icon (colored circle: green=connected, grey=idle, red=error).
- Keeps a single `Window` in the composition at all times with `visible=windowVisible`.
  **Do not use conditional rendering** (`if (visible) { Window(...) }`): removing the window
  from the composition tree kills the macOS event loop and breaks the tray menu.
- `bringToFront()` uses reflection into `com.apple.eawt.Application.requestForeground(true)`
  because UIElement apps cannot steal focus the normal way. After calling that, it sets
  `isAlwaysOnTop=true`, calls `toFront()`, then releases `isAlwaysOnTop` after 150 ms via
  a one-shot Swing timer so macOS has time to process the window ordering.

### `AppViewModel.kt` — state machine

Single source of truth. Holds `MutableStateFlow<AppState>` and exposes it as read-only to
the UI. All mutations go through here. Key behaviors:

- On init: merges baked keys (immutable) with stored keys (user-added), then auto-selects
  the first key if nothing is active.
- `toggleProxy()`: calls `startProxy()` or `stopProxy()`. Start writes config via key2json,
  then launches xray. Stop destroys the process and, if system proxy was on, disables it.
- `toggleSysProxy()`: independent of connect/disconnect — you can toggle the system proxy
  setting at any time. Persisted in `settings.json`.
- `activateKey()`: if currently running, stops, switches key, restarts.
- On exit: calls `stopProxy()` synchronously (blocking) so the system proxy is always cleaned
  up before the JVM exits.

### `XrayProcess.kt` — subprocess wrapper

Manages one xray process at a time.

**Starting:**
1. `ensureBinary()` — extracts the platform xray binary from JVM resources to `appDir/xray`
   on first run (skips if already there).
2. Runs `xray key2json --socks-port 10808 --http-port 10809 --api-port 8888 <uri>` and reads
   JSON from stdout. This delegates VLESS parsing to the Go `extra.Parse()` function in
   xray-core — the same function used by the Android app. No duplicate parser.
3. Writes the JSON to `appDir/config.json`.
4. Runs `xray run -c config.json` with `XRAY_LOCATION_ASSET=appDir`.

**Stopping:** `Process.destroy()`.

### `SysProxy.kt` — system proxy toggle

macOS: iterates all network services via `networksetup -listallnetworkservices`, then sets
SOCKS and HTTP(S) proxy on each to `127.0.0.1:10808/10809`. On disable, just turns the
proxies off (does not remove the server address).

Windows: writes `ProxyEnable`/`ProxyServer` to `HKCU\...\Internet Settings`. Uses HTTP port
only (Windows system proxy is HTTP; SOCKS is handled per-app).

### `KeyStore.kt` / `BakedKeys.kt` — key persistence

**User keys** are stored in `appDir/keys.json` as a JSON array of `VlessKey`. Baked keys are
never written to this file.

**Baked keys** are vless:// URIs embedded at compile time in the `baked_keys.txt` JVM resource
(generated by the `generateBakedKeys` Gradle task from `-PbakedKeys`). On each launch they are
re-merged at the top of the key list. Their IDs are `baked:<hash>` so the same key across app
versions never duplicates.

Baked keys cannot be deleted by the user (no delete button rendered).

### `Updater.kt` — self-update

Hits the GitHub releases API for `0xCLWN/green-desktop`. Result is cached in `settings.json`
for 24 h. If the latest release tag is semver-newer than `APP_VERSION` (generated at build time
into `green/Version.kt`), an update banner appears in the UI. Clicking Install downloads the
platform asset (DMG or MSI) to the system temp dir and calls `open` / `cmd /c start` on it.
The user manually runs the installer — the app does not replace itself.

### `SettingsStore.kt` — persistent settings

`appDir/settings.json`. Fields: `sysProxyEnabled`, `updateCheckedAt`, `updateTag`,
`updateUrl`. `ignoreUnknownKeys = true` so old settings files survive upgrades.

## xray-core fork

Submodule at `xray-core/`, pointing to `github.com/0x1488/Xray-core`.

The fork adds:
- `extra/` package — `Parse(uri string) (*conf.Config, error)` that turns a `vless://` URI
  into a full xray config struct. This is the single source of truth for VLESS parsing, shared
  with the Android app (via gomobile) and the `key2json` CLI.
- `main/commands/all/key2json.go` — CLI subcommand that calls `extra.Parse()` and prints JSON
  to stdout. Flags: `--socks-port`, `--http-port`, `--api-port`.

To rebuild the binary after changing xray-core:

```
make xray-mac        # darwin/arm64
make xray-windows    # windows/amd64
make xray-all        # both
```

Binaries land in `composeApp/src/desktopMain/resources/xray/` and are bundled into the app
by jpackage.

## Data directory

| Platform | Path |
|----------|------|
| macOS    | `~/Library/Application Support/green-desktop/` |
| Windows  | `%APPDATA%\green-desktop\` |

Files written there at runtime:

| File | Contents |
|------|----------|
| `keys.json` | User-added VLESS keys |
| `settings.json` | Persisted settings (see above) |
| `config.json` | Last generated xray config (overwritten on each Start) |
| `xray` / `xray.exe` | xray binary extracted from app resources on first run |

## Build system

### Gradle tasks (composeApp/build.gradle.kts)

- `generateVersion` — writes `green/Version.kt` with `const val APP_VERSION = "x.y.z"`.
  Version is defined once as `appVersion` in the build script.
- `generateBakedKeys` — reads `-PbakedKeys` (comma-separated vless:// URIs) and writes
  `baked_keys.txt` into resources. Pass empty string to produce a resource-less build.
- `packageDmg` / `packageMsi` — jpackage bundles a JRE + the app into a self-contained
  installer. The user just runs it, no separate JRE needed.

### Makefile

Wraps the common workflows: build xray binaries, run in dev mode, package with/without baked
keys. The `XRAY_DIR` variable defaults to the submodule but can be overridden.

### GitHub Actions (`.github/workflows/release.yml`)

Triggers on `v*` tags and on manual dispatch (with optional `baked_keys` input).
Two parallel jobs — `build-mac-arm64` and `build-windows` — each check out with submodules,
build the xray binary, run jpackage, and upload the artifact. A third `release` job downloads
both artifacts and creates a GitHub release. Baked keys come from the `BAKED_KEYS` repo secret
or the workflow dispatch input.

## Ports

| Port | Protocol | Purpose |
|------|----------|---------|
| 10808 | SOCKS5 | Local proxy inbound |
| 10809 | HTTP | Local proxy inbound |
| 8888 | gRPC | xray API (stats, health) |

All ports are hardcoded. The API port is only opened when xray is running.

---

## Things that are intentionally absent

- **No x86 Mac support.** Only arm64. Removing it simplified CI and the xray build matrix.
- **No Linux packaging.** Targets are macOS and Windows only.
- **No auto-restart / watchdog.** If xray crashes, the UI shows an error and the user clicks
  Start again.
- **No self-replacing update.** The installer is downloaded and opened; the user runs it.
  Avoids needing elevated permissions or a helper daemon.
